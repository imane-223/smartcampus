# Conventions du projet SmartCampus

Document de référence pour les quatre membres de l'équipe. Chaque membre prend un
module de bout en bout ; ces règles évitent les conflits et gardent le code homogène.

## 1. Organisation des packages

Un package par module, les couches à l'intérieur :

```
com.smartcampus
├── config/        configuration commune (SecurityConfig, CorsConfig)
├── common/        ErrorResponse, exceptions partagées
├── auth/          comptes et connexion
│   ├── model/         entités JPA et enums
│   ├── repository/    interfaces Spring Data
│   ├── service/       logique métier
│   ├── controller/    endpoints REST
│   └── dto/           objets échangés avec le frontend
├── room/          salles et espaces (même découpage)
└── reservation/   réservations (même découpage)
```

- Ne modifiez que votre package. Une modification de `config/`, `common/` ou du
  package d'un autre module passe par une PR à part, annoncée à l'équipe.
- Un module n'accède aux données d'un autre que par son **service**, jamais
  directement par son repository.

## 2. Migrations Flyway

- Le schéma est géré **uniquement** par Flyway : `src/main/resources/db/migration`.
  Hibernate ne crée rien (`ddl-auto=validate`) : il vérifie seulement que les
  entités correspondent aux tables, et l'application refuse de démarrer sinon.
- Nommage : `V<n>__<sujet>.sql`, avec deux tirets bas, le sujet en minuscules et en snake_case.
  - `V1__utilisateurs.sql` (fait)
  - `V2__espaces.sql`, `V3__reservations.sql` (réservés)
  - Avant de créer une migration, annoncez son numéro à l'équipe pour éviter les doublons.
- **Une migration fusionnée dans `main` ne se modifie plus jamais.** Pour corriger,
  écrivez une nouvelle migration (`V4__...`). Flyway refuse de démarrer si une
  migration déjà appliquée a changé.
- **SQL portable PostgreSQL / H2 obligatoire.** Les tests exécutent les mêmes
  migrations sur H2 (mode PostgreSQL). Autorisé :
  - `BIGINT GENERATED BY DEFAULT AS IDENTITY` pour les clés primaires ;
  - `VARCHAR(n)`, `TEXT`, `INTEGER`, `BIGINT`, `BOOLEAN`, `DATE`, `TIMESTAMP WITH TIME ZONE` ;
  - `CONSTRAINT ... UNIQUE / CHECK / FOREIGN KEY`, `CREATE INDEX`.

  Écrivez la forme standard `TIMESTAMP WITH TIME ZONE` plutôt que l'alias `timestamptz`.
  Comme les tests exécutent les migrations sur H2, une syntaxe non portable fait
  échouer `./mvnw clean package` : lancez-le avant chaque PR.
  À proscrire, car propre à PostgreSQL : types `ENUM` (`CREATE TYPE`), `EXCLUDE USING gist`,
  fonctions plpgsql. Si une contrainte propre à PostgreSQL est indispensable
  (ex. non-chevauchement des réservations), on en discute d'abord : elle
  demandera Testcontainers.

## 3. Tables et colonnes

- Noms en **français**, en minuscules et en snake_case. Tables au pluriel (`utilisateurs`, `espaces`,
  `reservations`), colonnes au singulier (`courriel`, `mot_de_passe_hash`).
- Clé primaire : `id`. Clé étrangère : `<entite>_id` (`espace_id`, `demandeur_id`).
- Contraintes nommées : `uk_<table>_<colonne>`, `ck_<table>_<regle>`,
  `fk_<table>_<colonne>`, `idx_<table>_<colonne>`.
- Une contrainte `UNIQUE` crée déjà un index : n'en ajoutez pas un second.
- Énumérations stockées en `VARCHAR` avec une contrainte `CHECK`, et mappées en
  Java avec `@Enumerated(EnumType.STRING)`.
- Courriels toujours stockés **en minuscules**. L'entité les normalise, et une
  contrainte `CHECK` le garantit en base.

## 4. Entités JPA

- Champs Java en anglais pour les mots-clés techniques, mais les attributs
  métier gardent le nom de la colonne en camelCase (`motDePasseHash`, `creeLe`).
- Si le nom par défaut ne correspond pas à la colonne, précisez `@Column(name = ...)`.
  Par exemple, `verrouilleJusquA` donnerait `verrouille_jusqua`.
- **Dates et heures : `java.time.Instant`**, jamais `LocalDateTime`. La colonne
  correspondante est `TIMESTAMP WITH TIME ZONE`. Avec `validate`, un
  `LocalDateTime` sur cette colonne empêche le démarrage. Pour une date seule
  (sans heure), utilisez `LocalDate` sur une colonne `DATE`.
- **`cree_le` est posé par l'entité** dans une méthode `@PrePersist`
  (`Instant.now()`), et non par un `DEFAULT now()` en base. La valeur est ainsi
  connue dès l'enregistrement, sans relire la ligne. La colonne est `NOT NULL`
  sans défaut, et `@Column(updatable = false)`. Même règle pour `modifie_le` avec `@PreUpdate`.
- Constructeur sans argument `protected`, exigé par JPA.

## 5. DTO

- Des `record` Java dans le package `dto` du module.
- Suffixes : `XxxRequest` pour ce qui arrive du frontend, `XxxResponse` pour ce qui
  part. Exemple : `LoginRequest`, `UserResponse`.
- Validation par Bean Validation sur les `Request` (`@NotBlank`, `@Email`...), avec
  `@Valid` dans le contrôleur.
- Un contrôleur ne renvoie **jamais** une entité JPA, uniquement des DTO.
  Cela évite d'exposer `mot_de_passe_hash` par accident.
- JSON en camelCase, dates au format ISO-8601 UTC (`2026-10-31T22:15:00Z`).

## 6. Format JSON des erreurs

Toutes les erreurs renvoient le même objet (`com.smartcampus.common.ErrorResponse`) :

```json
{
  "status": 400,
  "error": "VALIDATION",
  "message": "La justification est obligatoire.",
  "path": "/api/reservations",
  "timestamp": "2026-10-31T22:15:00Z",
  "fields": { "justification": "ne doit pas être vide" }
}
```

- `error` : un code stable en majuscules, que le frontend peut tester
  (`VALIDATION`, `UNAUTHORIZED`, `FORBIDDEN`, `CSRF`, `NOT_FOUND`, `CONFLICT`,
  `INVALID_CREDENTIALS`, `ACCOUNT_DISABLED`, `ACCOUNT_LOCKED`).
- `message` : en français, lisible par l'utilisateur.
- `fields` : seulement pour les erreurs de validation (absent sinon).
- `retryAt` : instant ISO-8601 (UTC) à partir duquel réessayer, quand il y en a un
  (absent sinon). La réponse porte alors aussi l'en-tête HTTP `Retry-After` (en secondes).

### Dates et heures dans les messages

**Aucune heure locale dans un message produit par le serveur.** Les conteneurs
tournent en UTC, les utilisateurs sont en Africa/Casablanca : une heure écrite par
le serveur serait fausse. Le serveur donne soit une **durée relative**
(« Réessayez dans 12 minutes. », arrondie à la minute supérieure), soit un
**instant ISO-8601** dans un champ JSON (`retryAt`, `debut`, ...). C'est le frontend
qui convertit l'instant dans le fuseau de l'utilisateur.

## 6 bis. Sécuriser un endpoint

Toute requête est authentifiée par défaut. Seuls sont publics : `POST /api/auth/login`,
`GET /api/auth/csrf` et `/actuator/health`. **N'ajoutez aucune URL publique sans
en parler à l'équipe.**

Deux niveaux, toujours les deux :

1. **Règle par préfixe** dans `config/SecurityConfig` : le premier filet, déjà en place.
   - `/api/admin/**` → rôle ADMIN
   - `/api/salles/**` et `/api/reservations/**` → utilisateur connecté
2. **`@PreAuthorize` sur chaque méthode de contrôleur** : la règle précise. Si un
   endpoint n'a pas d'annotation, la revue de code le refuse.

Exemple complet (module `room`) :

```java
package com.smartcampus.room.controller;

@RestController
@RequestMapping("/api/salles")
public class SalleController {

    private final SalleService salleService;

    public SalleController(SalleService salleService) {
        this.salleService = salleService;
    }

    // Consultation : tout utilisateur connecté
    @GetMapping
    @PreAuthorize("isAuthenticated()")
    public List<SalleResponse> lister(@RequestParam(required = false) TypeEspace type) {
        return salleService.lister(type);
    }

    // Création : administrateur uniquement
    @PostMapping
    @PreAuthorize("hasRole('ADMIN')")
    public ResponseEntity<SalleResponse> creer(@Valid @RequestBody SalleRequest request) {
        return ResponseEntity.status(HttpStatus.CREATED).body(salleService.creer(request));
    }

    // Utilisateur courant : jamais d'identifiant pris dans la requête pour « moi »
    @PostMapping("/{id}/signalements")
    @PreAuthorize("hasAnyRole('STUDENT', 'TEACHER')")
    public SignalementResponse signaler(@PathVariable Long id, @Valid @RequestBody SignalementRequest request,
            @AuthenticationPrincipal AuthenticatedUser user) {
        return salleService.signaler(id, request, user.id());
    }
}
```

- Rôles : `hasRole('STUDENT')`, `hasRole('TEACHER')`, `hasRole('ADMIN')`. Les
  autorités sont `ROLE_STUDENT`, `ROLE_TEACHER` et `ROLE_ADMIN`.
- L'utilisateur connecté s'obtient par `@AuthenticationPrincipal AuthenticatedUser`
  (`id`, `courriel`, `role`). C'est un résumé en session, pas l'entité : relisez la
  base si vous avez besoin de plus.
- Une règle qui dépend des données (« seulement ses propres réservations ») se
  vérifie dans le **service**, pas seulement dans l'annotation (règle R13 : droits
  vérifiés côté serveur à chaque requête).
- Réponses : **401** `UNAUTHORIZED` sans session, **403** `FORBIDDEN` avec le mauvais
  rôle, **403** `CSRF` si le jeton manque. Ces réponses sont produites par
  `SecurityConfig` : ne les renvoyez pas à la main depuis un contrôleur.
- **CSRF** : tout POST, PUT, PATCH ou DELETE doit porter l'en-tête `X-XSRF-TOKEN`
  avec la valeur du cookie `XSRF-TOKEN` (le frontend l'obtient par `GET /api/auth/csrf`).
  Le jeton change après la connexion.
- **Tests** : pour un utilisateur connecté, placez un `SecurityContext` en session
  (voir `AuthorizationTest.sessionAs`). Pour le jeton CSRF, utilisez
  `com.smartcampus.support.RealCsrf.from(mvc)`. **N'utilisez pas `csrf()` de
  spring-security-test** : il remplace durablement le dépôt CSRF du filtre et fausse
  les tests suivants du même contexte. Chaque endpoint teste au moins : 401 sans
  session, 403 avec un mauvais rôle, succès avec le bon rôle.
- Cookie de session : `SameSite=Lax` suffit en développement (`localhost:5173` et
  `localhost:8081` sont le même site, le port ne compte pas). **En production sur
  deux domaines distincts, il faudra `SameSite=None` et `Secure`** (HTTPS obligatoire).

## 6 ter. Frontend (`frontend/`)

React + Vite + TypeScript, react-router. Pas de framework CSS ni de bibliothèque
de composants : styles dans `src/index.css`, à partir des variables `:root`.

### Organisation

```
frontend/src/
├── api/          client.ts (client HTTP unique) + un fichier par module : auth.ts, salles.ts...
├── auth/         AuthProvider, useAuth (authState.ts), ProtectedRoute, libellés des rôles
├── pages/        une page par fichier : LoginPage.tsx, HomePage.tsx, SallesPage.tsx...
├── test/         setup.ts, faux backend fakeApi (api.ts)
└── App.tsx       routes
```

Chaque membre ajoute `api/<module>.ts`, ses pages dans `pages/`, ses routes dans `App.tsx`.

### Appeler l'API

- **Toujours `apiFetch`** (`api/client.ts`), jamais `fetch` directement. Il ajoute
  `credentials: 'include'` et l'en-tête CSRF sur POST, PUT, PATCH et DELETE. Il
  transforme aussi toute erreur en `ApiError`, et signale une session expirée.
- Les types TypeScript reprennent les DTO du backend, avec les mêmes noms de
  champs : `User` ↔ `UserResponse`.

  ```ts
  // api/salles.ts
  export interface Salle { id: number; code: string; nom: string; typeEspace: string; statut: string }

  export function listerSalles(type?: string): Promise<Salle[]> {
    return apiFetch<Salle[]>(type ? `/api/salles?type=${encodeURIComponent(type)}` : '/api/salles')
  }

  export function creerSalle(salle: Omit<Salle, 'id'>): Promise<Salle> {
    return apiFetch<Salle>('/api/salles', { method: 'POST', body: salle })
  }
  ```
- **CSRF** : rien à faire, `apiFetch` relit le cookie `XSRF-TOKEN` avant chaque
  requête (il change après la connexion et la déconnexion), le décode avec
  `decodeURIComponent`, et l'obtient par `GET /api/auth/csrf` s'il manque.
- **Erreurs** : attrapez `ApiError` et affichez `error.message`, déjà en français.
  `error.fields` donne le détail des champs en 400, et `error.code` le code stable
  (`FORBIDDEN`, `CONFLICT`...) pour réagir sans comparer des textes.
- **Session expirée** : tout 401 (sauf sur le login) efface l'utilisateur du
  contexte, et `ProtectedRoute` renvoie vers `/login`. Ne gérez pas le 401 page par page.
- **Dates** : le serveur envoie des instants ISO-8601 en UTC. Affichez-les dans le
  fuseau du navigateur avec `Intl.DateTimeFormat('fr-MA', ...)`, et ne recalculez
  jamais une heure à la main.

### Pages

- Une page protégée se place dans `<ProtectedRoute>` dans `App.tsx`. L'utilisateur
  courant s'obtient par `useAuth().user`. Masquer un bouton selon le rôle ne
  remplace pas le contrôle serveur (`@PreAuthorize`) : c'est seulement du confort.
- **Formulaires** : un vrai `<form onSubmit>`, avec `event.preventDefault()`, jamais
  un bouton `onClick`. La touche Entrée doit valider.
  - Chaque champ a un `<label htmlFor>` et un `autoComplete` adapté.
  - Le bouton est désactivé pendant l'envoi.
  - L'erreur s'affiche dans un élément `role="alert"`.
- **Accessibilité** : focus visible (déjà dans le CSS), contrastes suffisants,
  titres `h1` puis `h2`, texte des boutons explicite.
- Interface en français, avec les accents.

### Tests

- Vitest + Testing Library, fichier `*.test.tsx` à côté de la page.
- Cherchez les éléments comme un utilisateur : `getByRole`, `getByLabelText`.
  Évitez les sélecteurs CSS et les `data-testid`.
- Simulez le backend avec `fakeApi` (`src/test/api.ts`) : clé `"MÉTHODE /chemin"`,
  réponse `{ status, body }`. Aucun test n'appelle le vrai serveur.
- Chaque page teste au moins : l'affichage, le cas d'erreur (message du serveur
  dans l'alerte) et le cas nominal.
- Avant chaque PR : `npm run test` et `npm run build` (Jenkins ne les lance pas encore).

## 7. Langue

| Élément | Langue |
|---|---|
| Base de données (tables, colonnes) | français |
| Mots-clés techniques Java (suffixes de couche, méthodes) | anglais : `UtilisateurRepository`, `AuthService`, `findBy...`, `login()` |
| Entités et attributs métier | français : `Utilisateur`, `Etudiant`, `courriel` |
| Messages destinés à l'utilisateur | français, **avec les accents** |
| Commits | `SC1-<n> Verbe au présent ...` (clé Jira obligatoire) |

## 8. Lancer le projet en local

Prérequis : JDK 21, Docker.

```bash
docker compose up -d db          # PostgreSQL 16 sur localhost:5432
./mvnw spring-boot:run           # application sur http://localhost:8081
./mvnw clean package             # build + tests (H2, sans PostgreSQL)
cd frontend && npm install && npm run dev   # interface sur http://localhost:5173 (pile Docker requise)
```

- Valeurs par défaut (développement uniquement) : base `smartcampus`, utilisateur
  et mot de passe `smartcampus`. On les surcharge par les variables `DB_URL`,
  `DB_USER`, `DB_PASSWORD` et `SERVER_PORT`.
- Si une variable `DB_PASSWORD` est déjà définie sur votre poste, elle remplace la
  valeur par défaut.
- Si le port 5432 est déjà pris (PostgreSQL installé sur le poste), arrêtez ce
  service ou lancez l'application avec `DB_URL` pointant vers un autre port.
- Tests : profil `test` (`@ActiveProfiles("test")`) sur tout test qui charge un
  contexte Spring.
- **Comptes de démonstration** : propriété `smartcampus.demo-data.enabled`
  (variable `SMARTCAMPUS_DEMO_DATA_ENABLED`). **Désactivée par défaut**, et elle doit le
  rester partout sauf en développement : les mots de passe de démonstration sont
  publics (README). Le `compose.yaml` l'active pour la pile Docker locale. En local :
  `SMARTCAMPUS_DEMO_DATA_ENABLED=true ./mvnw spring-boot:run`. Ne créez pas d'autre
  mécanisme de données de démonstration : complétez `config/DataInitializer`, qui est
  idempotent (il ne crée que ce qui manque).
